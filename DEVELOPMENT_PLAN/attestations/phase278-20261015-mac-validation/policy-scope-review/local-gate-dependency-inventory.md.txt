## Source freshness audit: historical phase gates versus global standing gates

Read-only follow-up at candidate `b519dfa6206cd2350711d12ce1916922b50eff9c3b7db63800dbc58e89fe89cb` (383 files). No implementation, gate, ownership, status or evidence pin is changed.

**Finding: a later Phase279 detector-only source edit does NOT, by itself, invalidate an earlier Phase278 GateTranscript obligation.** The code already prevents that particular backward host-order cycle. Do not confuse the source stamp retained inside every record with a requirement that every consumer compare it to today's tree.

Exact path:

- `Product/SourceDigest.hs:12-31,78-85,115-136` hashes all eligible files under app/gen/src/test and both Cabal project files. A detector implementation or test edit normally changes the global Haskell source stamp even when no training recipe changes.
- `Product/ValidationRecord.hs:209-233,413-446` records/adopts that stamp along with the actual gate, substrate, command and outcome. Admission does not compare the stamp against current source; that is a consuming-obligation choice.
- `Product/StatusLoader.hs:426-448,454-498` judges a genuine transcript by its gate/substrate, exact unfiltered standing command, required live mode and Passed outcome. It retains the source stamp in `TranscriptEvidence`. `loadEvidenceIndexIn:661-682` computes current source separately.
- `Product/StatusEvidence.hs:193-203` explicitly defines `GateTranscript` as historical and `StandingGate` as requiring the current tree, explaining that per-sprint Done must not evaporate when a later sprint edits code.
- `observeObligation:327-335` returns `transcriptJudgement` directly for GateTranscript; only StandingGate invokes `freshTranscript:378-408`, where differing source algorithms/digests become Unproven/Stale.
- `projectSprint:659-685` derives a phase from its owned obligations and upstream phases. It does not include global standing obligations. `projectStatusReport:640-652` checks standing obligations separately; `closureVerdict:697-707` uses their refusals for the whole-product verdict.
- `Product/PhaseStatus.hs:96-102` currently declares global StandingGate unit, negative-controls and model-convergence on LinuxCPU. Existing per-phase obligations (including278/279) use GateTranscript, not StandingGate. The proposed local-gate ownership design must preserve this distinction.
- `test/unit/JournalDerivedStatus.hs:777` explicitly accepts a historical transcript despite its age/source. The test at849-868 proves an otherwise closed catalogue keeps every sprint Done when one global standing transcript becomes stale, while whole-product closure is refused. This is established behavior, not a proposed freshness relaxation.

Consequently, under the PROPOSED ownership split,278 can complete genuine local CPU/Apple GateTranscripts on its frozen source, then279 can implement its detector on the NVIDIA host. Those later source-only changes stale the global CPU StandingGate records; they require new current-source global unit/negative/model validation later, as intended. They do not automatically reopen278 or demand revisiting the Apple host solely because of the HaskellSourceStamp. No new pinned/source exception is needed or justified.

Lane journals are different. `Test/ProductLaneJournal.hs:97-114` has a digest of the authenticated source journal, not the global HaskellSourceStamp. Its current admission checks include current ProductRow PlanId and scenario contract digest (`validateProjected:610-638`), plus full row coverage, binding, evidence and pinned journal checks. `StatusEvidence.hs:336-343` reobserves LaneJournal/Aggregate obligations, and its header31-39 explains that current-contract evidence becoming stale can demote an owning phase. A detector implementation alone need not change a recipe/PlanId or scenario contract; an actual recipe, completion-policy, projection or pinned-journal change can. If279 discovers and repairs a training/policy defect that changes a lane contract still owned by278, those lane obligations can genuinely reopen278. That is the existing semantic/source-freeze risk, not a universal GateTranscript freshness cycle.

A second independent caveat is canonical record replacement: transcript files are keyed by gate and lane. A later genuine Failed run replacing a previously Passed file makes the historical GateTranscript judgement Unproven by OUTCOME, even though source staleness alone would not. Preserve all superseded bytes; never force a Passed pin to avoid reporting a real later failure. Reusing the same local gate in both phases therefore still requires a clean successful implementation and final validation, not immutable historical immunity to new failures.

The tracked governance proposal's broad statement that source-bound records become stale after later source edits should be read as referring to GLOBAL STANDING validation and any changed recipe/contract evidence, not all historical per-sprint GateTranscripts. This ignored inventory supplies the narrower exact-code qualification; the proposal itself remains unimplemented and no tracked prose is changed here.
